# F06 提供方案与点赞

> **代码位置**：后端 `service/SolutionService.create` / `like`、`controller/SolutionController`；前端 `pages/detail/detail.js` 方案区
> **状态**：✅ 已实现（列表排序存在缺陷，见第 9 节）
> **最后更新**：2026-11-26

## 1. 功能定位

竞品只能"在发起者给的选项里选一个"，这个功能让用户**补充发起者没想到的第三条路**。它把产品从"投票工具"改成"众包解法库"——一个正在纠结的人不只能看到多数人怎么选，还能看到别人想出了什么自己没考虑到的方案。

方案可以被打分：点赞代表"我觉得这路可行"，采纳代表"我真的走了这条路"（见 F07）。

## 2. 用户视角流程

1. 详情页方案区标题是"还有别的路吗？"，下面一行说明"如果你经历过类似的事，给出一个发起者没想到的方案"
2. 输入方案内容（≤500 字）→ 提交
3. 方案列表展示：作者昵称、作者星星与代表场景标签、"已采纳"角标、内容、点赞数
4. 点 ♡ 点赞，再点取消（切换式）
5. 发起者视角下，每条未采纳方案右侧有"采纳"按钮

## 3. 业务规则

| 规则 | 说明 |
|---|---|
| 内容长度 | ≤500 字，必填，过内容安全 |
| 归属校验 | 帖必须存在，否则 404「这个话题不存在」 |
| 点赞唯一 | `UNIQUE (solution_id, user_id)`；再次点赞即**取消点赞** |
| 点赞计数 | `dv_solution.like_count` 冗余字段，插入/删除同事务内 ±1，便于排序 |
| 可见范围 | 只返回 `status = 1` 的方案 |
| 排序 | 意图：已采纳优先 → 点赞数倒序 → 时间倒序 |
| 我的标记 | `mine = true` 表示当前用户提交的方案 |
| 发起者也能提交 | 不受限制，但自己给自己点赞没有业务价值（未禁止） |

**方案列表返回字段（`SolutionVO`）**

| 字段 | 说明 |
|---|---|
| id / content / createdAt | 基本信息 |
| likeCount / liked | 点赞数、我是否赞过 |
| adopted | 是否被发起者采纳 |
| mine | 是否我提交的 |
| authorName / authorAvatar | 作者展示信息 |
| authorStars | 作者总星星数（跨场景求和） |
| authorSceneTag | 作者星星最高的场景，作为代表标签 |

## 4. 数据结构

**表 `dv_solution`**

| 字段 | 说明 |
|---|---|
| post_id / user_id | 归属 |
| content | 方案内容 |
| adopted | 1 = 被发起者采纳 |
| like_count | 冗余点赞数 |
| status | 1 正常 / 0 隐藏 |

**表 `dv_solution_like`**：`solution_id` + `user_id`，唯一索引。

## 5. 接口

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/posts/{id}/solutions` | 必须 | 提交方案，返回 `{id}` |
| GET | `/api/posts/{id}/solutions` | 可选 | 方案列表（带我的点赞态） |
| POST | `/api/solutions/{id}/like` | 必须 | 点赞/取消点赞 |

**POST 提交方案**
```json
{ "content": "先别接，用两个月复盘 + 接外包过渡，现金流守住的同时保留选择权" }
```

**GET 方案列表响应**
```json
{
  "code": 0,
  "data": [
    {
      "id": 5,
      "content": "先别接…",
      "likeCount": 7,
      "liked": false,
      "adopted": true,
      "mine": false,
      "authorName": "想清楚的428",
      "authorStars": 3,
      "authorSceneTag": "职场",
      "createdAt": "2026-11-26 19:02:11"
    }
  ]
}
```

## 6. 后端实现

| 方法 | 关键逻辑 |
|---|---|
| `create` | 查帖 → 过审 → 落库（`adopted=0`、`like_count=0`、`status=1`） |
| `like` | 尝试 insert → 成功则 `incrementLike`；捕获 `DuplicateKeyException` → 删除该点赞并 `decrementLike`（切换式点赞） |
| `list` | SQL 层 `orderByDesc(adopted, likeCount, createdAt)` → 逐条 `toVO` |
| `toVO` | 查作者、查作者 `dv_user_credit` 求总星星、取 stars 最高的场景作为标签、查我的点赞态 |

点赞用"先插入再捕获重复"实现切换，而不是先查后写——避免并发下的检查-写入竞态。

## 7. 前端实现

| 方法 | 职责 |
|---|---|
| `onSolutionInput` / `addSolution` | 输入与提交，成功后清空输入并重拉列表 |
| `likeSolution` | 调接口后重拉列表（未做本地乐观更新） |
| WXML | 采纳角标、作者星星徽标、场景标签、`liked` 切换 ♥/♡ |

提交方案与点赞都走"调用后整列表重拉"，实现简单但会带来一次额外请求。

## 8. 边界与异常

| 场景 | 表现 |
|---|---|
| 内容为空 / 超 500 字 | `@Valid` 400 |
| 帖不存在 | 404 |
| 方案不存在或已隐藏 | 404「方案不存在」 |
| 重复点赞 | 视为取消点赞，返回成功（幂等语义） |
| 未登录点赞 | 401 |
| 点赞后列表刷新失败 | 计数已在库中变更，下次进入页面即正确 |

## 9. 已知限制与待办

- [ ] **排序缺陷（需尽快修）**：`SolutionService.list` 里的比较器
  `comparing(isAdopted).reversed().thenComparingInt(likeCount).reversed()`
  末尾的 `.reversed()` 反转了整个组合比较器，实际效果是**未采纳的排在已采纳前面**，与"已采纳置顶"的设计相反。修复方式是拆开写：
  `comparing(SolutionVO::isAdopted).reversed().thenComparing(comparingInt(SolutionVO::getLikeCount).reversed())`
- [ ] **N+1 查询**：每条方案都要查作者、查信用记录、查点赞态（3 次 SQL），方案多时慢。`dv_user` 加 `stars` 冗余字段、批量查 `dv_user_credit` 可解
- [ ] 无编辑/删除自己的方案
- [ ] 点赞无本地乐观更新，弱网下手感偏慢
- [ ] 未做"方案被采纳后作者收到通知"
- [ ] 方案不支持图片、参考链接
