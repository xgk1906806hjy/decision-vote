# F11 内容安全与举报

> **代码位置**：后端 `service/ContentAuditService`、`service/ReportService`、`controller/ReportController`、`controller/WxCallbackController`；前端 `pages/detail` 举报入口
> **状态**：✅ 内容安全、举报提交、举报处置后台、头像异步送审均已实现；生产需配置真实微信、`WX_MEDIA_TOKEN` 与 `ADMIN_TOKEN`
> **最后更新**：2026-11-27

## 1. 功能定位

UGC 产品的合规底线。两件事：

- **发前拦截**：所有用户输入（标题、描述、选项、方案、建议、昵称、简介、经历）过一遍内容安全，命中违禁内容直接拒绝；
- **发后兜底**：用户可以举报违规的决策或评论，平台据此下架。

对个人主体小程序来说，这两项直接决定能不能过审、能不能活下去。

## 4. 数据结构

**表 `dv_report`**（举报提交已使用；处置后台未实现）

| 字段 | 说明 |
|---|---|
| target_type | `post` / `comment` |
| target_id | 被举报对象 ID |
| user_id | 举报人 |
| reason | 举报理由 |
| handled | 0 待处理 / 1 已处理 |
| created_at | 时间 |

索引 `idx_target (target_type, target_id)`。

**表 `dv_media_check`**（头像异步送审，见第 9 节）

| 字段 | 说明 |
|---|---|
| trace_id | 微信异步审核任务 ID，`uk_trace` 唯一，回调靠它认领记录 |
| user_id | 送审用户 |
| media_path | 站内相对路径（`/uploads/avatar/...`），清头像时用来比对「是不是同一张」 |
| suggest | 回调结果 `pass` / `review` / `risky` |
| status | `0` 待回调 / `1` 通过 / `2` 违规已重置 / `3` 检测失败 |

索引 `uk_trace(trace_id)`、`idx_user(user_id)`。

## 5. 接口

**举报提交已实现**，内容安全仍是服务内方法，不对外暴露。

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/reports` | 必须 | 举报 `{targetType: post\|comment, targetId, reason}` |

处理顺序（任一步失败即返回 400/404，不写库）：

1. `targetType` 必须在 `post` / `comment` 白名单内，否则「不支持的举报类型」；
2. 目标必须存在：`post` 查 `dv_post`、`comment` 查 `dv_comment`，不存在返回 404；
3. 不能举报自己发布的内容，否则「不能举报自己发布的内容」；
4. 同一用户对同一目标只记一次，重复提交返回「你已经举报过了，我们会尽快处理」。

`reason` 限 255 字，`handled` 初始写 0。

**举报处置后台**（请求头 `X-Admin-Token`，令牌由 `ADMIN_TOKEN` 配置）：

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/admin/reports?handled=0&page=1&size=20` | 管理员 | 列表；`handled=0` 待处理、`1` 已处理、`-1` 全部 |
| POST | `/api/admin/reports/{id}/handle` | 管理员 | `{action: hide\|dismiss}`；hide 隐藏内容，dismiss 驳回 |
| GET | `/admin/reports.html` | 管理员令牌 | 静态处置页，输入令牌后查看/操作 |

`hide` 对决策帖执行逻辑删除（`deleted=1`），对建议写 `status=0`；处置后记录 `handled=1`、`action`、`handled_at`。静态页只做同源请求，不额外引入前端框架。

**微信消息推送回调**（微信服务器调用，不走 JWT，`WebConfig` 已放行）：

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/wx/callback?signature=&timestamp=&nonce=&echostr=` | 签名 | 配置回调地址时的有效性校验，验签通过后原样返回 `echostr` |
| POST | `/api/wx/callback?signature=&timestamp=&nonce=` | 签名 | 收 `wxa_media_check` 事件，兼容 JSON 与 XML |

签名 = `sha1(sort(token, timestamp, nonce))`，`token` 即 `WX_MEDIA_TOKEN`；用 `MessageDigest.isEqual` 比对，避免时序侧信道。**Token 未配置时直接拒绝**——不提供「空 token 放行」的后门。

## 6. 后端实现

`ContentAuditService.check(text)` 先过本地词库（硬拦截 + 提示性词），再根据 `app.content.audit-mock` 决定是否调用微信：

1. `audit-mock=true`：只走本地词库，本地开发默认值；
2. `audit-mock=false`：用当前登录用户的 `openid` 调 `wxa/msg_sec_check`，`scene` 默认 3（论坛），`version=2`；
3. `suggest=risky` 直接拒绝，`suggest=review` 提示修改后再试；
4. 微信接口异常时，`fail-open=false`（默认）直接返回 500 拦截，`fail-open=true` 才降级为本地词库并记录错误日志；
5. `access_token` 在 `WxApiService` 内缓存，提前 5 分钟过期；失效错误码 40001/42001 自动刷新重试一次。

`UserService` 在更新昵称/简介时也调了 `audit.check`，但**没有校验 avatar URL**（外部图片地址可被滥用）。举报理由也会过一遍内容安全。

## 7. 前端实现

`pages/detail` 有两个举报入口：

1. 正文卡右下角「举报该内容」，提交 `targetType=post`；
2. 每条建议右下角「举报」，提交 `targetType=comment`。

两个入口共用 `reportTarget(targetType, targetId)`：

1. `wx.showActionSheet` 弹原因列表：违法违规内容 / 色情低俗 / 广告营销 / 人身攻击 / 虚假信息；
2. 选中后调 `api.report({targetType, targetId, reason})`；
3. 成功 toast「已收到举报，我们会尽快处理」，失败直接把后端 `msg` 弹出来；
4. `reporting` 状态位在请求期间拦住重复点击。

后台页 `backend/src/main/resources/static/admin/reports.html`：输入 `ADMIN_TOKEN` 后加载待处理列表，可隐藏内容或驳回举报；令牌存 `sessionStorage`，不写入 URL。

其余输入框不做前端检查，全部依赖后端返回错误文案后 Toast 提示。

## 8. 边界与异常

| 场景 | 表现 |
|---|---|
| 命中硬拦截词 | 400，提示修改后再试 |
| 命中提示性词 | 400，提示注意用语 |
| 词库未覆盖的违规内容 | **直接发布成功**——这是当前最大风险 |
| 变体绕过（拼音、拆字、谐音、图片） | 无任何识别能力 |
| 用户被骚扰/辱骂但未命中词库 | 可走举报入口，但**举报后没有处置后台**，`handled` 始终为 0 |
| 举报后无反馈 | 用户只能看到「已收到」，之后没有任何状态回传 |
| 头像违规 | 上传时当场看不出，回调到达后 `avatar` 被清空；用户下次打开「我的」会发现自己头像没了，属预期行为 |
| 回调地址不可公网访问 | 送审能拿到 `trace_id`，但结果永远推不回来，`status` 停在 0，等于没审 |
| `WX_MEDIA_TOKEN` 未配置 | 回调一律视为验签失败并拒绝，等同未接入 |
| 送审接口故障 | 只打 warn 日志，上传照常成功——宁可漏审一张，也不阻断用户传图 |
| 回调重复推送 | 按 `trace_id` 找回记录并覆盖写，重复推送不会产生多条记录 |

## 9. 头像异步送审（mediaCheckAsync）

文字能同步判，图片不能。微信的图片审核是**异步**的：提交后只返回一个 `trace_id`，结果稍后推到你配置的回调地址。所以头像的策略是「先让用户用上，违规再回收」。

### 9.1 提交流程

`FileController.avatar` 落盘成功后调 `submitMediaCheck`，四道前置判断依次短路：

| 步骤 | 逻辑 |
|---|---|
| 1 落盘 | 校验通过即存文件并返回 url，**送审不阻塞响应** |
| 2 `AUDIT_MOCK=true` | 直接跳过（本地开发不产生真实审核费用，也不会污染记录） |
| 3 URL 不是 `http` 开头 | 说明 `UPLOAD_PUBLIC_BASE` 没配，微信拉不到图 → 跳过并 warn |
| 4 openid 为空或以 `mock_` 开头 | mock 登录造的身份微信不认识 → 跳过 |

通过后调 `WxApiService.mediaCheckAsync`，参数 `media_type=2`（图片）、`version=2`、`scene=1`（资料）；`errcode` 为 `40001/42001` 时刷新 token 重试一次。拿到 `trace_id` 后写入 `dv_media_check`，`status=0`。

任何一步抛异常都只记 warn，**上传接口仍然返回成功**。

### 9.2 回调流程

`WxCallbackController` 收到 `wxa_media_check` 事件后按 `trace_id` 找回记录：

| 回调内容 | 处理 |
|---|---|
| `errcode != 0` | `status=3`（检测失败），头像不动 |
| `suggest=pass` | `status=1`，通过 |
| `suggest=review` | `status=1` 且保留 `suggest`，**当前等同放行**，留给人工复核 |
| `suggest=risky` | `status=2`，并清空用户头像 |

清头像前会做一次比对：当前 `dv_user.avatar` 必须仍包含这条记录的 `media_path`。否则用户期间已经换了新头像，直接清就等于误伤。

两个实现细节：

- 解析 XML 时关掉 DTD 与外部实体（`disallow-doctype-decl`），防 XXE；JSON / XML 两种推送格式都支持，因为公众平台的数据格式是可选的；
- 无论内部处理成功与否都返回 `success`，让微信停止重试——重复推送对我们无害（按 `trace_id` 覆盖写），但重试风暴会打满日志。

### 9.3 为什么必须落库

回调是「无状态的一次 HTTP 推送」，body 里只有 `trace_id`、`errcode`、`suggest`，**不告诉你这是谁、哪张图**。没有 `dv_media_check` 做映射，收到也就是干瞪眼。
