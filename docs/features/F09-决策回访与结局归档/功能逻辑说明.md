# F09 决策回访与结局归档

> **代码位置**：后端 `service/FollowUpService`、`service/FollowUpReminderService`、`service/SubscribeService`、`job/FollowUpReminderJob`、`service/PostService.create`（建计划）；前端 `pages/detail/detail.js` 回访区、`pages/profile/profile.js` 待回访 + 回访提醒
> **状态**：✅ 已实现（含订阅消息主动提醒；模板 ID 需在微信公众平台申请后填入配置）
> **最后更新**：2026-11-27

## 1. 功能定位

产品的**护城河**。竞品都在"决策那一刻"就结束了，而用户真正的痛点是"我当年那么选，到底对不对"。

回访机制在决策发布时就埋下时间点（3 个月后），到期后请发起者回来填：**最后选了哪条、现在觉得值得还是后悔、有什么想说的**。这些数据沉淀成"决策 → 真实结局"的链路，随时间复利增值，是后来者抄不走的部分。

## 2. 用户视角流程

1. **发布决策时自动埋点**：系统建一条回访计划，`due_at = 发布 + 3 个月`，用户无感
2. 「我的 → 回访提醒」点「开启提醒」，微信弹一次性订阅授权框，同意后额度 +1
3. 3 个月后到期当天 **10:00**，微信服务通知推一条「该说说结果了」，点开直达该决策详情页
4. 没开提醒也能在"我的 → 待回访"看到，显示"应于 08-26 回访"
5. 点进去 → 详情页回访区（仅发起者可见）→ 展开表单
6. 表单三项：**最终选择了哪个选项（必选）**、结果标签（值得/后悔/还在观察）、一段心得
7. 提交 → 提示"已记录，进入案例库" → 该决策立即出现在案例库
8. 详情页顶部展示结局：最终选择 + 结果标签 + 心得；其他人也能看到

## 3. 业务规则

| 规则 | 说明 |
|---|---|
| 计划生成 | `PostService.create` 内自动创建，`due_at = now + 3 个月`，`answered_at` 为空 |
| 填写权限 | 仅发起者，否则 403「只有发起人可以填写结果」 |
| 结果标签 | 必须是 `worth` / `regret` / `watching`；可空（后端允许只填选项不填标签） |
| 前端约束 | **必须选择最终结果**才能提交（`choseOptionId` 非空），后端未强制 |
| 一帖一回访 | `dv_follow_up` 上 `UNIQUE KEY uk_post`，一帖只能有一条回访记录 |
| 重复提交 | 为覆盖更新（upsert），`answered_at` 刷新为当前时间 |
| 待回访判定 | `answered_at IS NULL` 且 `due_at <= now`，按 `due_at` 升序，最多 20 条 |
| 进入案例库 | 唯一条件就是 `answered_at` 非空——**填了结局即入案例库**，无人工审核 |
| 详情透出 | 已回访的帖子，详情返回 `chosenOptionId`、`outcome`、`outcomeNote`、`outcomeSlot="已回访"` |

### 3.1 订阅消息提醒规则

微信的一次性订阅消息是**「授权一次 = 可发一条」**，不能长期订阅，所以后端把"授权"记成额度，而不是一个布尔开关。

| 规则 | 说明 |
|---|---|
| 额度来源 | 前端 `wx.requestSubscribeMessage` 返回 `accept` 后调 `POST /api/subscribe/follow-up`，`remain + 1` |
| 额度上限 | 单用户最多囤积 `app.subscribe.max-remain`（默认 10）次，防止反复点按刷额度 |
| 消耗时机 | 发送**成功**（errcode=0）才 `remain - 1`；未发出去不扣 |
| 发送时间 | 每天 10:00（`app.subscribe.cron`），错过不补发，第二天继续（`reminded_at` 为空的还会被捞到） |
| 候选口径 | `answered_at IS NULL` 且 `due_at <= now` 且 `reminded_at IS NULL`，且 `due_at >= now - max-age-days`（默认 7 天） |
| 为什么要 age 上限 | 用户可能几个月不打开小程序，一次给他翻出一堆旧账只会被当成骚扰，直接取关 |
| 幂等 | 发完立刻写 `reminded_at`，任务重复执行也不会重发 |
| 无额度 | **不**写 `reminded_at`，等用户下次授权后同一帖还能再推 |
| 用户拒收（43101）/ 模板参数错（47003） | 额度清零 + 写 `reminded_at`，避免每轮都撞同一面墙 |
| 其他错误（网络/微信 5xx） | 不写 `reminded_at`，下一轮自动重试 |
| 帖子已删/账号异常 | 写 `reminded_at` 后跳过，不再扫描 |
| 未配置模板 | 任务直接跳过并返回 `template-not-configured`，不影响其他功能（降级） |
| 单轮上限 | 最多处理 `batch-size`（默认 50）条，防止一次打爆微信接口频率限制 |

## 4. 数据结构

**表 `dv_follow_up`**

| 字段 | 说明 |
|---|---|
| post_id | 唯一键，一帖一条 |
| user_id | 发起者 |
| chose_option_id | 最终选了哪个选项 |
| outcome | worth / regret / watching |
| note | 心得，≤1000 字 |
| due_at | 计划回访时间（发布 + 3 月） |
| answered_at | 实际填写时间，非空即"已回访" |
| reminded_at | 订阅消息提醒时间，非空表示已推过，任务不再捞 |
| created_at | 创建时间（发布时即创建） |

索引 `idx_due (answered_at, due_at)` 支撑"到期未填"查询。

**表 `dv_subscribe`（一次性订阅额度）**

| 字段 | 说明 |
|---|---|
| user_id + tmpl_id | 联合唯一，一个用户一个模板一行 |
| tmpl_id | 模板别名，当前固定 `follow-up`（未用真实模板 ID，换模板不影响历史额度） |
| remain | 剩余可发送次数：授权 +1、发送成功 -1 |
| created_at / updated_at | 审计用 |

额度与"是否已提醒"是两件事：额度管**能不能发**，`dv_follow_up.reminded_at` 管**这一条发过没有**。分开存的好处是用户重新授权后，旧记录不会被误判为已推。

## 5. 接口

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/posts/{id}/follow-up` | 必须 | 提交/覆盖回访结果 |
| GET | `/api/follow-ups/pending` | 必须 | 我到期未回访的决策 |
| GET | `/api/subscribe/follow-up` | 必须 | 查询剩余提醒次数 + 模板是否就绪 |
| POST | `/api/subscribe/follow-up` | 必须 | 授权成功后额度 +1 |
| GET | `/api/admin/reminders?limit=` | 管理员令牌 | 预览本轮候选（不发送、不扣额度） |
| POST | `/api/admin/reminders/run` | 管理员令牌 | 手动触发一轮发送 |

**POST 请求**
```json
{
  "choseOptionId": 42,
  "outcome": "regret",
  "note": "薪资是涨了，但期权没谈，两年后看亏了一大截"
}
```

**GET /api/follow-ups/pending 响应**
```json
{
  "code": 0,
  "data": [
    { "postId": 18, "title": "35 岁被裁，要不要接降薪 30% 的 offer", "dueAt": "2027-02-26 19:02:11" }
  ]
}
```

**GET/POST /api/subscribe/follow-up 响应**
```json
{
  "code": 0,
  "data": { "remain": 1, "maxRemain": 10, "templateReady": true }
}
```

**POST /api/admin/reminders/run 响应**
```json
{
  "code": 0,
  "data": { "status": "ok", "candidates": 2, "sent": 2, "noQuota": 0, "failed": 0 }
}
```

`status` 取值：`ok` 正常执行、`template-not-configured` 未配模板、`wx-mock` 本地 mock 环境不发真实消息。

## 6. 后端实现

| 方法 | 关键逻辑 |
|---|---|
| `FollowUpService.submit` | 查帖 → 校验归属（403）→ 校验标签枚举 → 按 `post_id` 查已有记录 → 有则更新、无则插入 → `answered_at = now` |
| `FollowUpService.pending` | `answered_at IS NULL AND due_at <= now`，升序取 20 → 批量查标题组装 |
| `PostService.create` | 建帖后立刻插入回访计划（同事务） |
| `PostService.detail` | 查回访记录，`answered_at` 非空才透出结局字段 |
| `FollowUpReminderService.dueList` | 到期未填 + 未提醒 + 在 age 窗口内，按 `due_at` 升序取 `batch-size` |
| `FollowUpReminderService.runOnce` | 前置判断（模板/mock）→ 批量查帖与 openid → 逐条校验额度 → 组装模板数据 → 发送 → 按 errcode 决定扣额度/作废/留待重试 |
| `FollowUpReminderService.buildData` | `thing1` 标题（截断 20 字，`thing` 类型超长会 47003）、`time2` 计划回访时间、`thing3` 引导语 |
| `WxApiService.sendSubscribeMessage` | 调 `cgi-bin/message/subscribe/send`，token 失效（40001/42001）自动刷新重试一次，异常不外抛只返回 errcode |
| `FollowUpReminderJob` | `@Scheduled(cron = app.subscribe.cron)`，异常捕获后只记日志，不影响其他定时任务 |
| `SubscribeService` | 额度查/增/扣/清零，全部按 `(user_id, follow-up)` 定位；`remain` 上限用 `min` 夹住 |

## 8. 边界与异常

| 场景 | 表现 |
|---|---|
| 非发起者提交 | 403 |
| 未选最终结果 | 前端 Toast「请选择最终结果」；后端会接受（不校验），属规则不一致 |
| 重复提交 | 覆盖原记录，`answered_at` 刷新，案例库按新时间排序 |
| 待回访为空 | 前端不渲染该区块 |
| 帖已删除 | 待回访展示"已删除的话题" |
| 未配置订阅模板 | 提醒卡提示"当前环境未配置模板"，后端任务返回 `template-not-configured` 并跳过，其余功能不受影响 |
| 用户拒绝授权 | 前端 Toast「未开启，随时可以再来」，不落额度、不报错 |
| 用户中途改主意（微信里关掉通知） | 发送返回 43101 → 额度清零 + 标记已提醒，避免每轮重试 |
| 本地 mock 环境（`WX_MOCK=true`） | 任务返回 `wx-mock` 跳过；想看候选可开 `FOLLOW_UP_DRY_RUN=true` |
| 同一帖只推一次 | `reminded_at` 挡住重复推送；用户从推文点进来却没填，第二天不会再来催 |

## 9. 已知限制与待办

- [x] ~~**无主动触达（最关键）**~~ 已解决：接入微信一次性订阅消息，每天 10:00 推送到期提醒
- [ ] **提醒只发一次**：用户点开看了但没填，第二天不会再催——微信一次性订阅额度已消耗。可考虑"填完才给星星"或页面内二次挽留
- [ ] **授权是摩擦点**：`requestSubscribeMessage` 必须用户主动点击，且每次只能囤一次额度。理想做法是在「发布决策成功」的下一步顺势请求（用户刚付出成本，同意率最高），目前只在「我的」页提供入口
- [ ] **多轮回访缺失**：一帖一条记录（`uk_post`），无法做"3 个月 / 1 年 / 3 年"多轮追踪。产品设想的多时点回访需要改成 `(post_id, round)` 结构，届时 `reminded_at` 也要按轮次拆
- [ ] 回访时间固定 3 个月，用户不可选
- [ ] 后端不强制 `choseOptionId` 非空，与前端规则不一致
- [ ] 回访不可撤回；填错只能再填一次覆盖，无历史版本
- [ ] 未做"结局与当初建议的对照"（如"当年 87% 建议他跳，他跳了，一年后后悔"），这是案例价值最大的呈现方式，尚未计算
