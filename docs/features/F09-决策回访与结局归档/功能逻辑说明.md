# F09 决策回访与结局归档

> **代码位置**：后端 `service/FollowUpService`、`service/PostService.create`（建计划）；前端 `pages/detail/detail.js` 回访区、`pages/profile/profile.js` 待回访
> **状态**：✅ 已实现（无主动推送，只能进"我的"页看到期）
> **最后更新**：2026-11-26

## 1. 功能定位

产品的**护城河**。竞品都在"决策那一刻"就结束了，而用户真正的痛点是"我当年那么选，到底对不对"。

回访机制在决策发布时就埋下时间点（3 个月后），到期后请发起者回来填：**最后选了哪条、现在觉得值得还是后悔、有什么想说的**。这些数据沉淀成"决策 → 真实结局"的链路，随时间复利增值，是后来者抄不走的部分。

## 2. 用户视角流程

1. **发布决策时自动埋点**：系统建一条回访计划，`due_at = 发布 + 3 个月`，用户无感
2. 3 个月后，该决策出现在"我的 → 待回访"，显示"应于 08-26 回访"
3. 点进去 → 详情页回访区（仅发起者可见）→ 展开表单
4. 表单三项：**最终选择了哪个选项（必选）**、结果标签（值得/后悔/还在观察）、一段心得
5. 提交 → 提示"已记录，进入案例库" → 该决策立即出现在案例库
6. 详情页顶部展示结局：最终选择 + 结果标签 + 心得；其他人也能看到

## 3. 业务规则

| 规则 | 说明 |
|---|---|
| 计划生成 | `PostService.create` 内自动创建，`due_at = now + 3 个月`，`answered_at` 为空 |
| 填写权限 | 仅发起者，否则 403「只有发起人可以填写结果」 |
| 结果标签 | 必须是 `worth` / `regret` / `watching`；可空（后端允许只填选项不填标签） |
| 前端约束 | **必须选择最终结果**才能提交（`choseOptionId` 非空），后端未强制 |
| 一帖一回访 | `dv_follow_up` 上 `UNIQUE KEY uk_post`，一帖只能有一条回访记录 |
| 重复提交 | 为覆盖更新（upsert），`answered_at` 刷新为当前时间 |
| 待回访判定 | `answered_at IS NULL` 且 `due_at <= now`，按 `due_at` 升序，最多 20 条 |
| 进入案例库 | 唯一条件就是 `answered_at` 非空——**填了结局即入案例库**，无人工审核 |
| 详情透出 | 已回访的帖子，详情返回 `chosenOptionId`、`outcome`、`outcomeNote`、`outcomeSlot="已回访"` |

## 4. 数据结构

**表 `dv_follow_up`**

| 字段 | 说明 |
|---|---|
| post_id | 唯一键，一帖一条 |
| user_id | 发起者 |
| chose_option_id | 最终选了哪个选项 |
| outcome | worth / regret / watching |
| note | 心得，≤1000 字 |
| due_at | 计划回访时间（发布 + 3 月） |
| answered_at | 实际填写时间，非空即"已回访" |
| created_at | 创建时间（发布时即创建） |

索引 `idx_due (answered_at, due_at)` 支撑"到期未填"查询。

## 5. 接口

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/posts/{id}/follow-up` | 必须 | 提交/覆盖回访结果 |
| GET | `/api/follow-ups/pending` | 必须 | 我到期未回访的决策 |

**POST 请求**
```json
{
  "choseOptionId": 42,
  "outcome": "regret",
  "note": "薪资是涨了，但期权没谈，两年后看亏了一大截"
}
```

**GET /api/follow-ups/pending 响应**
```json
{
  "code": 0,
  "data": [
    { "postId": 18, "title": "35 岁被裁，要不要接降薪 30% 的 offer", "dueAt": "2027-02-26 19:02:11" }
  ]
}
```

## 6. 后端实现

| 方法 | 关键逻辑 |
|---|---|
| `FollowUpService.submit` | 查帖 → 校验归属（403）→ 校验标签枚举 → 按 `post_id` 查已有记录 → 有则更新、无则插入 → `answered_at = now` |
| `FollowUpService.pending` | `answered_at IS NULL AND due_at <= now`，升序取 20 → 批量查标题组装 |
| `PostService.create` | 建帖后立刻插入回访计划（同事务） |
| `PostService.detail` | 查回访记录，`answered_at` 非空才透出结局字段 |

## 7. 前端实现

| 位置 | 职责 |
|---|---|
| `detail.js → toggleFollowUp` | 展开/收起回访表单；入口仅在 `post.author` 为真时渲染 |
| `detail.js → onFollowChosen` | 选择最终选项，再点取消 |
| `detail.js → submitFollowUp` | 校验已选最终结果 → 提交 → 关闭表单 → 重拉详情 |
| `profile.js → loadPending` | 拉待回访列表，把 `dueAt` 格式化为"应于 MM-DD 回访" |
| `detail.wxml` 结局区 | 已回访时展示"最终选择 / 结果标签 / 心得" |

## 8. 边界与异常

| 场景 | 表现 |
|---|---|
| 非发起者提交 | 403 |
| 未选最终结果 | 前端 Toast「请选择最终结果」；后端会接受（不校验），属规则不一致 |
| 重复提交 | 覆盖原记录，`answered_at` 刷新，案例库按新时间排序 |
| 待回访为空 | 前端不渲染该区块 |
| 帖已删除 | 待回访展示"已删除的话题" |

## 9. 已知限制与待办

- [ ] **无主动触达（最关键）**：到期后用户收不到任何提醒，只能自己进"我的"看到期列表。需接微信**订阅消息**并在发布/回访时引导授权，否则回访率会很低
- [ ] **只有一次回访**：一帖一条记录（`uk_post`），无法做"3 个月 / 1 年 / 3 年"多轮追踪。产品设想的多时点回访需要改成 `(post_id, round)` 结构
- [ ] 回访时间固定 3 个月，用户不可选
- [ ] 后端不强制 `choseOptionId` 非空，与前端规则不一致
- [ ] 回访不可撤回；填错只能再填一次覆盖，无历史版本
- [ ] 未做"结局与当初建议的对照"（如"当年 87% 建议他跳，他跳了，一年后后悔"），这是案例价值最大的呈现方式，尚未计算
