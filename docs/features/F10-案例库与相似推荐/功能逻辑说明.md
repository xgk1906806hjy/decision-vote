# F10 案例库与相似推荐

> **代码位置**：后端 `service/CaseService`、`controller/CaseController`；前端 `pages/cases/*`（案例库）、`pages/create/create.js`（相似推荐）
> **状态**：✅ 已实现
> **最后更新**：2026-11-26

## 1. 功能定位

把回访数据变成**可检索的人生决策档案**。用户不是来投票的，而是来查"和我情况差不多的人，当年怎么选、现在怎么样"。

这直接改变了产品的使用性质：从低频的"纠结时才来提问"，变成可反复查阅的参考库。同一个能力在发起页复用为"相似案例推荐"——写决策前先看看别人的结局。

## 2. 用户视角流程

**案例库页**
1. tabBar 第二项进入，展示已回访的案例列表（标题、场景、结局标签、最终选择、心得、参与人数）
2. 顶部场景 chip 筛选，输入关键词搜索（标题/描述包含匹配），可一键清空
3. 上拉加载更多、下拉刷新
4. 点击进入详情页，看完整案例（与决策详情同页，额外展示结局）

**发起页推荐**
1. 在发起决策页选中场景后，自动加载 3 条同场景案例
2. 卡片展示标题 + 结局标签，点进去可参考

## 3. 业务规则

| 规则 | 说明 |
|---|---|
| 入池条件 | `dv_follow_up.answered_at` 非空（即已回访），**仅此一条** |
| 已删除帖 | `dv_post.deleted = 1` 的跳过 |
| 场景筛选 | 精确匹配 `post.scene` |
| 关键词 | 标题或描述 `contains`，任一命中即可 |
| 排序 | 按 `answered_at` 倒序（最近回访的在前） |
| 分页 | 内存分页，`size` 上限 50，`hasMore = to < total` |
| 结局标签 | 后端直接给中文：`worth` → 值得、`regret` → 后悔、`watching` → 观察中，缺省"已有结局" |
| 相似度算法 | 同场景 +60 分；关键词逐字命中，每字 +5，上限 40 分；按分数倒序取前 `limit`（默认 5，上限 20） |

## 4. 数据结构

不新增表，聚合 `dv_follow_up`（筛已回访）+ `dv_post` + `dv_option`（最终选择 label）+ `dv_vote` + `dv_comment`。

**`CaseVO` 字段**

| 字段 | 说明 |
|---|---|
| postId / title / content / scene | 决策基本信息 |
| outcome / outcomeLabel | 结果标签原值 + 中文 |
| outcomeNote | 心得 |
| chosenLabel | 最终选择的选项文案 |
| answeredAt | 回访时间 |
| voteCount / commentCount | 参与度 |
| similarity | 相似度分数（仅推荐接口有意义） |

## 5. 接口

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/cases?page=1&size=10&scene=&keyword=` | 否 | 案例列表 |
| GET | `/api/cases/similar?scene=&keyword=&limit=5` | 否 | 相似案例推荐 |

## 6. 后端实现

| 方法 | 关键逻辑 |
|---|---|
| `CaseService.list` | 一次捞出**所有**已回访记录（按 `answered_at` 倒序）→ 批量查帖子 → Java 内存里过滤 scene/keyword → 内存分页 |
| `CaseService.similar` | 复用 `list(1, 200, scene, null)` 取候选 → 逐条打分 → 排序 → `limit` |
| `CaseService.toCase` | 组装结局、最终选择 label、票数、评论数 |

**注意**：过滤与分页都在 Java 内存里完成，SQL 只做"取已回访"。这是当前实现的最大性能隐患（见第 9 节）。

## 7. 前端实现

| 位置 | 职责 |
|---|---|
| `pages/cases/cases.js → loadCases(reset)` | 分页加载，`reset` 决定覆盖/追加 |
| `onSceneTap` / `onSearch` / `clearKeyword` | 筛选与搜索，均回到第 1 页 |
| `viewState` | 区分 `empty`（无任何案例）与 `empty-filter`（筛选无结果），后者文案引导放宽条件 |
| `pages/create/create.js → loadSimilarCases` | 选场景后 `limit=3` 拉推荐，失败静默清空不阻塞发布 |

案例卡片点击复用 `pages/detail/detail`，不单独做案例详情页——同一份数据，多展示"结局"区块即可。

## 8. 边界与异常

| 场景 | 表现 |
|---|---|
| 案例库为空 | `viewState = 'empty'`，文案引导"还没有案例，去做第一个吃螃蟹的人" |
| 筛选无结果 | `empty-filter`，文案提示换个场景或关键词 |
| 关键词含中文 | 前端 `wx.request` 自动编码；后端 `@RequestParam` 正常解码（冒烟脚本曾因未编码失败，见改动记录） |
| 帖已删除 | 跳过，不出现在案例库 |
| 回访记录有但帖子查不到 | `post == null` 时跳过，不抛错 |

## 9. 已知限制与待办

- [ ] **全量内存过滤（性能红线）**：`list` 每次请求都把**所有已回访记录**捞进内存再过滤分页。案例到几千条时接口会明显变慢、内存抖动。应改为 SQL 层 `JOIN + WHERE + LIMIT`，并给 `dv_post.scene`、`title` 建索引
- [ ] **相似度算法过于粗糙**：按"单字符是否出现"计分，没有分词、没有语义，容易把不相关的案例排到前面。可先改为场景 + 阶段标签的多维匹配，或接大模型做语义相似
- [ ] 无"按结局筛选"（只看后悔的案例，恰恰是最有价值的一类）
- [ ] 无收藏、无"我也遇到过"标记
- [ ] 案例库未展示"当初多数人怎么建议 vs 他实际怎么选"的对照，价值最高的信息没算出来
- [ ] 冷启动无种子内容，空案例库会让首屏很难看，需先手工灌 20–30 条真实案例
