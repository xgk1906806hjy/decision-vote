## 1. 产品背景

人的一生会面临大量不可逆的重大决策：要不要辞职考研、要不要接这个降薪 offer、要不要为了伴侣换城市、要不要回老家考编。这类决策有三个共性：

1. **没有标准答案**，只有"适不适合我"；
2. **后果延迟暴露**，往往三五年后才知道当年选得对不对；
3. **决策成本高**，选错轻则经济损失，重则多走数年弯路。

用户当前的替代方案都很差：问身边人（样本小、立场偏、不敢说真话）、发帖问网友（大多是随口一评）、搜索经验帖（信息零散、无法验证结果）。

**核心缺口：市面上能拿到"多数人的意见"，但拿不到"走过这条路的人的真实结局"。**

## 2. 产品定位

> **让走过这条路的人告诉你结果，而不是让陌生人替你数票。**

现有投票类产品（拿个主意吧、钱包请等等、缓缓买等）本质是**投票工具**：发起者预设 A/B/C，用户投票，票数最高即答案。它们优化的是"参与量"和"投票体验"，但都止步于决策发生的那一刻。

本产品把链条往后延长：

| 环节 | 竞品做法 | 本产品做法 |
|---|---|---|
| 选项来源 | 只有发起者预设 | 发起者预设 **+ 全网补充方案**（众包解法） |
| 投票过程 | 实时显示票数，从众效应强 | **盲投**，投完才揭晓 |
| 建议质量 | 谁都能答，无法分辨真假经历 | 带**经历档案**与**结果标签**（值得/后悔/观察中） |
| 价值归属 | 无沉淀 | 方案被采纳得**星星 + 系统标签**，形成可信度 |
| 决策之后 | 到此结束 | **结局回访**，沉淀"决策—结局"数据资产 |
| 内容形态 | 一次性讨论 | **案例库**，可检索、可推荐给相似决策 |

产品类别因此从"投票器"变为**"人生决策案例库 + 众包解法平台"**。

## 3. 目标用户

### 3.1 决策者（发起人）
正处在纠结期，需要一个决定。特征是焦虑、信息不足、希望听到"和我情况类似的人后来怎样"。
诉求：发出问题 → 拿到结构化的方案和证词 → 做出选择 → 日后回填结果。

### 3.2 过来人（方案/建议提供者）
已经走过这条路，有真实结果。动机是被认可（星星、标签）。
诉求：我的经历有价值，能被采纳、被点赞、被记住。

### 3.3 围观者（案例读者）
还没到决策点，或正在做同类决策。动机是参考。
诉求：快速查到"和我相似的人怎么选、结果如何"。

### 3.4 典型使用场景
- 小陈拿到两个 offer，一个稳定一个高薪，纠结两周，发帖后收到 3 条"我当年选了稳定，现在后悔"的过来人建议，以及 1 条他自己没想到的第三条路（谈薪后保留期权）。
- 小李想知道"30 岁转行还来不来得及"，直接进案例库筛选"30-35 岁 / 转行"，看到 12 条带结局记录，其中 8 条标"值得"。

## 4. 核心机制

### M1 结构化决策发布
发帖时必须填写：标题、详细处境、**场景标签**、**选项（2–6 个）**、是否匿名、投票期限。
场景标签是后续案例推荐、相似匹配、星星标签的基础设施，**不是可选项**。

### M2 盲投
投票前，用户只能看到"已有 N 人参与"，看不到任何选项的票数与百分比；投票成功后（或话题已截止）立即揭晓完整分布。
目的：消除从众效应，让每一票是独立判断。
设计细节：显示参与人数但不显示分布，保留参与感；揭晓时给出结果动画。

### M3 方案众包
除投票外，任何用户可提交**新方案**（发起者没想到的第三条路）。方案独立于预设选项，可被点赞、可被采纳。
目的：从"选哪个"升级为"还有什么路"。

### M4 采纳与星星标签
- **采纳权归发起者**，点赞数作为参考权重展示（发起者能看到"该方案 37 人点赞"），但决策权不被票数绑架。
- 采纳成功后：方案作者 **+1 星**，并按该决策的**场景自动累计标签**（如"职场选择 ×3"）。
- 标签只能由系统按采纳记录生成，**禁止用户自封**。

### M5 结局回访
发起者在决策后回填：最终选了哪个、现在觉得值不值（值得/后悔/观察中）、补充说明。
系统记录 `due_at`（3 个月 / 6 个月 / 12 个月）并提醒回访；未回填的进入"待回访"列表。
数据以「决策 → 结局」结构永久保留，是该产品最难被复制的资产。

### M6 案例库与相似推荐
已回填结局的决策自动成为**案例**，进入案例库，支持按场景、关键词检索。
用户发起新决策时，按场景/关键词推荐相似历史案例，供其参考。
案例详情展示：当年的问题、最终选择、结局评价、多少人参与、多少人给过建议。

## 7. 业务规则

1. **投票**：`dv_vote` 上 `(post_id, user_id)` 唯一；一帖一票；截止后不可投。
2. **盲投判定**：`blind = !isAuthor && !hasVoted && status != closed`。发起者始终可见全部结果。
3. **方案**：一帖可多方案；同一用户可对同帖提多个方案（不限制）；内容长度 ≤ 500。
4. **采纳**：仅发起者可调用；采纳后 `adopted=1`；同一方案不可重复采纳（重复调用直接返回成功，不重复加星）。
5. **星星**：每被采纳一次 +1 星；按 `(user_id, scene)` 维度累计，总数 = 各场景之和。
6. **标签**：场景采纳次数 ≥1 即生成标签；展示优先级按星星数倒序。
7. **回访**：一帖一条 `dv_follow_up`；仅发起者可提交；提交后该帖进入案例库。
8. **案例**：`answered_at IS NOT NULL` 的决策才是案例。
9. **内容审核**：发帖、方案、建议三处均需过审，命中敏感词直接拒绝。

## 8. 合规与内容安全

- 服务类目按**工具**申报，避免被判为"社区/论坛"（个人主体难以过审）。
- 产品文案避免出现"社区""论坛""交友""广场"等社交化表述。
- 必须提供**举报入口**与**违规内容处理机制**。
- 接入微信 `security.msgSecCheck`（生产环境 `AUDIT_MOCK=false`），服务器出口 IP 需加白名单。
- 用户昵称、头像需走 `mediaCheckAsync`（P1）。
- 隐私协议需声明：收集 openid、用户内容、经历档案用途。

## 9. 数据指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 决策发布量 | 每日新增 dv_post | — |
| 投票参与率 | 有投票的帖子 / 总帖子 | > 60% |
| 方案贡献率 | 有方案的帖子 / 总帖子 | > 40% |
| 采纳率 | 有采纳的帖子 / 有方案的帖子 | > 30% |
| 回访完成率 | answered_at 非空 / 应回访数 | > 35% |
| 案例库规模 | answered_at 非空的帖子数 | 首月 100+ |

## 10. 版本规划

**V1.0（MVP，当前开发范围）**
发布决策 → 盲投 → 提交方案 → 点赞 → 采纳得星星 → 发表建议 → 回访回填 → 案例库浏览 → 相似推荐 → 我的主页。
目标：跑通一条完整闭环，能在真机上走完"发帖到回访"。

**V1.1**
订阅消息到期提醒、案例详情页增强、举报后台、我的页两个 Tab。

**V1.2**
同频匹配（按经历档案匹配回答者）、按维度打分（收入/成长/风险/家庭）、大模型意见归纳、少数派观点独立曝光。

## 11. 本期不做

- 排行榜、签到等增长玩法
